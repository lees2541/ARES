## 모델 반입 흐름 ([결정 기록](../05_결정/결정-기록.md) D-010)

모델 담당자가 Unity를 열지 않고도 올릴 수 있도록, 원본을 받는 곳과 프로젝트 에셋을 나눈다.

1. 모델 담당자가 `모델-업로드/<모델 이름>/`에 Tripo에서 받은 파일을 그대로 넣고 `main`에 push한다. 사용법은 `모델-업로드/읽어주세요.md`.
2. 개발 쪽(또는 AI)이 새로 들어온 모델을 Unity 프로젝트로 가져온다. 이때 이름을 정리하고 크기와 머티리얼을 확인한다.
   가져올 위치는 아래 "폴더 구조"를 따른다. 여러 던전이 함께 쓰는 모델은 `Assets/ARES/Common/<분류>/Art/`,
   한 던전에만 쓰는 모델은 `Assets/ARES/Dungeons/<던전 이름>/Art/`.
3. 원본은 `모델-업로드/`에 그대로 둔다. 고친 버전은 같은 폴더의 파일을 바꿔서 다시 올린다.

- `모델-업로드/`는 `Assets/` 밖이라 Unity가 읽지 않고 `.meta`도 생기지 않는다.
- 모델 형식 `.glb`, `.usdz`, `.3mf`를 Git LFS 규칙에 추가했다 (`.gitattributes`).
- `Assets/Resources/`에 있는 모델 두 개는 이 흐름을 정하기 전에 올라온 것이다.

## 폴더 구조 ([결정 기록](../05_결정/결정-기록.md) D-012)

**코드는 시스템별로, 콘텐츠는 던전별로** 모은다. 기획이 "모든 던전에 공통인 시스템"과 "던전 하나를 한 묶음으로 하는 콘텐츠"로
나뉘는 것([기획 파트 구성](../01_기획/기획-파트-구성.md))과 같은 기준이다. 프로토타입과 섞이지 않도록 본 작업은 `Assets/ARES/` 한 곳에 모은다.

```
Assets/
├─ ARES/                      본 작업 (dev 브랜치)
│  ├─ Scripts/                코드는 전부 여기에만 둔다
│  │  ├─ Runtime/             ARES.Runtime 어셈블리
│  │  │  ├─ Core/             게임 루프, Day 진행, 세이브, 여러 시스템이 함께 쓰는 공통 기반
│  │  │  ├─ Players/
│  │  │  ├─ Dungeons/         생성, 영속화
│  │  │  ├─ Entities/         엔티티 AI
│  │  │  ├─ Civilians/        민간인 AI, 구조
│  │  │  ├─ Rulebooks/        수칙서, 단서, 생존자 정보
│  │  │  ├─ Facilities/       유도표시, 안전지대
│  │  │  ├─ Management/       생존률, 지역 이벤트
│  │  │  ├─ UI/
│  │  │  └─ Network/          네트워크 연결과 동기화 기반 (D-014)
│  │  ├─ Editor/              ARES.Editor 어셈블리. 에디터 전용 도구
│  │  └─ Tests/               ARES.Tests 어셈블리 (테스트 패키지를 추가한 뒤)
│  ├─ Common/                 여러 던전이 함께 쓰는 콘텐츠
│  │  └─ Players/, Civilians/, Facilities/, UI/, Audio/
│  ├─ Dungeons/               던전 하나 = 폴더 하나
│  │  └─ <던전 이름>/         그 던전의 데이터, 프리팹, 아트, 사운드
│  └─ Scenes/
├─ Prototype/                 프로토타입 (prototype 브랜치). 본 작업 코드가 의존하지 않는다
├─ ThirdParty/                팀이 함께 쓰는 외부 에셋 (커밋한다)
├─ Settings/                  URP 설정
└─ Imports/, Test/            개인 로컬 전용 (커밋되지 않는다)
```

### 규칙

- **코드는 `Assets/ARES/Scripts/` 아래에만 둔다.** 던전 하나에만 쓰이는 동작도 코드는 해당 모듈에 두고, 던전별 차이는 데이터(ScriptableObject)로 표현한다.
- **콘텐츠 폴더의 하위 폴더는 필요한 것만 만든다:** `Data/`(ScriptableObject), `Prefabs/`, `Art/`(모델·머티리얼·텍스처·애니메이션), `Audio/`.
  예: `Dungeons/<던전 이름>/Data/`, `Common/Civilians/Art/`.
- **어셈블리 정의는 3개로 시작한다:** `ARES.Runtime`, `ARES.Editor`, `ARES.Tests`. 더 나누는 것은 필요해질 때 한다.
- **namespace는 모듈 폴더를 따른다:** `ARES.Dungeons`, `ARES.Rulebooks`. 모듈 이름은 복수형으로 쓴다.
  namespace 이름이 용어집의 타입 이름(`Dungeon`, `Rulebook`, `Player`)과 같으면 다른 파일에서 그 타입을 쓸 때 이름이 충돌하기 때문이다.
- **`Assets/` 안의 폴더·파일 이름은 영어**로, 띄어쓰기 없이 쓴다. `Docs/`와 `모델-업로드/`는 한글이어도 된다.
- **`Assets/Resources/`는 기본적으로 쓰지 않는다.** 안에 든 것이 전부 빌드에 포함된다. `Resources.Load`가 꼭 필요한 것만 예외로 둔다.
- **빈 폴더는 미리 만들지 않는다.** Git은 빈 폴더를 저장하지 않아 `.meta`만 남는다. 첫 파일을 넣을 때 폴더를 만든다.
- **외부 에셋:** 받아서 살펴보는 동안은 `Imports/`(개인)에 두고, 게임에 쓰기로 하면 `ThirdParty/`로 옮겨 커밋한다.
- 여기에 없는 새 최상위 폴더나 새 모듈 폴더가 필요하면 만들기 전에 PM에게 확인한다.

## Git 규칙 요약
- 브랜치와 병합은 아래 "브랜치와 병합 흐름"을 따른다
- 개인 폴더: `Assets/Imports/*`, `Assets/Test/*` (폴더와 `.gitkeep`만 공유)
- 바이너리는 LFS. 새 바이너리 확장자를 쓰면 `.gitattributes` 확인
- 씬은 여러 명이 동시에 고치지 않는다. 작업 씬을 나누거나 프리팹 단위로 작업
- `.meta`는 항상 에셋과 함께 커밋

### 브랜치와 병합 흐름 ([결정 기록](../05_결정/결정-기록.md) D-013)

```
main        문서·규칙(PM)과 모델 원본(정희성)이 직접 들어오는 곳
 │  ▲
 │  └─ dev를 올림: 플레이 가능한 상태가 됐을 때, PM이
 ▼
dev         본 작업. main을 수시로 받아 온다
 ▲
 └─ 작업 브랜치 (feat/<작업 이름>): PM이 검토한 뒤 합친다

prototype   프로토타입. main을 수시로 받아 온다. main으로는 올리지 않는다
 ▲
 └─ 작업 브랜치 (proto/<작업 이름 또는 본인 이름>): PM이 검토한 뒤 합친다
```

- **`main`, `dev`, `prototype`에는 PM만 합친다.** 예외는 `모델-업로드/`에 모델을 올리는 것 하나다.
- **아래로는 수시로, 위로는 검토 후에 보낸다.** `main`의 문서·규칙·모델은 바뀔 때마다 `dev`와 `prototype`으로 내려보낸다.
  작업 브랜치는 검토를 통과한 뒤 합치고, `dev`는 플레이 가능한 상태가 됐을 때 `main`으로 올린다.
- **PR은 쓰지 않는다.** 팀원이 자기 작업 브랜치를 push하고 PM에게 알리면, PM이 검토한 뒤 합친다.
  검토에서는 건드리면 안 되는 파일을 바꿨는지, 폴더 구조와 용어집 이름을 따랐는지, 기존 코드와 같은 역할의 코드를 새로 만들지 않았는지를 본다.
- **지금 상태 (2026-11-28 PM 전달):** `dev`는 기획이 확정된 뒤 본격적으로 쓴다. 그때까지는 대기 상태이고, 네트워크 패키지만 설치돼 있다.
  `prototype` 쪽은 PM이 임시로 만들어 시험하는 곳이다. 프로토타입에서 볼만해진 시스템은 나중에 `dev`로 옮긴다 (코드는 `dev`에서 새로 만든다).
- **작업 브랜치는 짧게 쓴다.** 합쳐지면 지운다. 작업 중에는 자기 줄기(`dev` 또는 `prototype`)를 받아 와 최신으로 유지한다.
- **`prototype`은 `main`으로 올리지 않는다.** 프로토타입은 검증용이고 본 작업이 의존하지 않는다. 본 작업에 쓸 것은 `dev`에서 새로 만든다.
- 강제 push, 원격 브랜치 삭제, 이미 올라간 커밋을 되돌리거나 다시 쓰는 것은 PM의 지시 없이 하지 않는다.

### 처음 클론한 뒤 한 번: 씬·프리팹 병합 도구 등록

`.gitattributes`는 씬·프리팹·에셋(YAML 파일)을 병합할 때 Unity의 UnityYAMLMerge를 쓰도록 되어 있다.
하지만 도구 경로는 저장소에 담기지 않으므로 **컴퓨터마다 한 번 등록**해야 한다. 등록하지 않으면 일반 텍스트 병합으로 처리되어 씬이 충돌하기 쉽다.

저장소 폴더에서 PowerShell 또는 Git Bash로 실행한다 (Unity를 기본 위치에 설치한 경우).

```
git config merge.unityyamlmerge.name "Unity SmartMerge (UnityYAMLMerge)"
git config merge.unityyamlmerge.driver "'C:/Program Files/Unity/Hub/Editor/6000.6.10f1/Editor/Data/Tools/UnityYAMLMerge.exe' merge -h -p --force --fallback none %O %B %A %A"
git config merge.unityyamlmerge.recursive binary
```

- Unity를 다른 위치에 설치했다면 경로를 바꾼다. 프로젝트의 Unity 버전을 올리면 경로의 버전 번호를 바꿔 다시 등록한다.
- 등록 확인: `git config --get merge.unityyamlmerge.driver`
- 도구가 자동으로 합치지 못한 부분은 Git 충돌로 남는다. 이때는 한쪽을 고르거나(`git checkout --ours <파일>` / `--theirs <파일>`) Unity에서 다시 작업한다.
